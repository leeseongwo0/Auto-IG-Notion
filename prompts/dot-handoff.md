# Dot 전달용 최종 작업 지시

## 목표와 대상

Instagram `@{{INSTAGRAM_USERNAME}}`의 기존 지표를 Meta Business Suite에서 수집하고, Notion에 새 성과 관리 공간을 구성하라. 기존 자료 최초 수집부터 반복 수집 준비까지 진행하라.

- 상위 Notion 페이지: {{NOTION_PARENT_PAGE_URL}}
- 이 페이지 아래에 새 `Instagram 성과` 하위 페이지를 만들고 세 DB를 구성한다.
- Business Suite를 기본 원본으로 사용한다. 필요한 지표를 여기서 모두 볼 수 있으면 Instagram 별도 로그인은 필수 조건이 아니다. 부족한 지표만 접근 가능한 Instagram 인사이트로 보완한다.
- 기존 Notion 기록과 기존 캘린더는 이관하지 않는다.

## 현재 상태

설계 문서와 샘플 웹 프로토타입만 준비되어 있다. 실제 Notion 페이지·DB 생성, 서비스 연결, 실제 데이터 수집·저장, 예약 실행은 아직 하지 않았다. 프로토타입 숫자는 전부 가상 데이터이므로 실데이터로 이관하지 않는다. 웹 목업은 구성 참고 자료이며 실제 작업은 Notion DB와 기본 보기로 구현한다.

저장소는 https://github.com/leeseongwo0/Auto-IG-Notion 이다. 접근 가능하면 `README.md`, 이 지시문, `notion/schema.json`, `docs/initial-import.md`를 읽고 상세 정의를 따른다. 실제 계정과 상위 Notion 주소는 사용자의 전달 메시지 또는 비공개 로컬 설정에서 읽는다. 공개 예제값을 실제 대상으로 쓰지 않는다. 저장소에 접근할 수 없더라도 이 지시문을 입력으로 받았다면 기본 구성을 진행할 수 있다.

## 만들 구조

1. `콘텐츠`: 게시물·릴스 하나당 한 행. 콘텐츠명(제목), 콘텐츠 키·계정 식별자·콘텐츠 식별자(텍스트), 원본 링크(URL), 종류(선택: 게시물/릴스), 게시일(날짜), 최신 조회·도달·좋아요·댓글·저장·공유(숫자), 최신 수집 시각(날짜), 최신 지표 상태·최근 수집 상태(선택), 최신 기록 키·최신 지표 비고·최근 수집 비고(텍스트), 최근 시도 시각(날짜), 최신 집계 범위(선택: 누적).
2. `콘텐츠 지표`: 콘텐츠의 날짜·집계 범위별 관측 한 행. 관측명(제목), 기록 키·계정 식별자·콘텐츠 식별자(텍스트), 콘텐츠(콘텐츠 DB와 관계), 원본 링크(URL), 관측일·수집 시각·집계 시작·집계 종료(날짜), 집계 범위(선택), 원본 기간 표기·원본 지표명·수집 비고·실행 ID(텍스트), 조회·도달·좋아요·댓글·저장·공유(숫자), 수집 상태(선택: 완료/부분 수집/확인 필요).
3. `계정 지표`: 계정의 날짜·집계 범위별 관측 한 행. 관측명(제목), 기록 키·계정 식별자(텍스트), 계정 링크(URL), 관측일·수집 시각·팔로워 수집 시각·집계 시작·집계 종료(날짜), 팔로워·조회·도달(숫자), 집계 범위(선택), 원본 기간 표기·원본 지표명·수집 비고·실행 ID(텍스트), 수집 상태(선택: 완료/부분 수집/확인 필요).

최신 지표 상태는 `미수집/검증 중/검증 완료`, 최근 수집 상태는 `미수집/완료/부분 수집/확인 필요`로 시작한다. 콘텐츠 지표의 집계 범위 선택값은 `누적/기간/미확인`, 계정 지표는 `기간/누적/순간값/미확인`이다. 일별·최근 30일 등의 세부 의미와 시간대는 원본 기간 표기에 보존한다.

대시보드에는 게시일 기준 콘텐츠 캘린더, 검증 완료된 최신 콘텐츠 성과 표, 콘텐츠 관측 이력, 계정 추이 표, 확인 필요 항목, 실제 수집·예약 상태를 배치한다. 단순 최댓값이나 합계 롤업을 최신값으로 사용하지 않는다. 계정의 과거 성과는 관측일이 아니라 원본 집계 기간을 기준으로 비교한다.

## 수집 범위와 실행 순서

1. 사용할 수 있는 도구와 로그인 상태, Business Suite의 대상 Instagram 계정, Notion 상위 페이지와 쓰기 권한을 확인한다. 연결이 없으면 필요한 서비스만 구체적으로 알리고 독립적으로 가능한 작업은 계속한다.
2. 상위 페이지 아래에서 대상 계정과 `Auto-IG-Notion · schema v1` 표식이 일치하는 구성을 찾는다. 검증된 구성이 하나면 재사용한다. 없으면 생성하며, 같은 이름의 불완전한 후보는 이전 실행 기록과 대조해 복구하거나 충돌로 보고한다. 이름만 보고 덮어쓰거나 중복 생성하지 않는다. 생성한 페이지·DB URL을 즉시 기록한다.
3. 콘텐츠 한 건과 계정 한 건을 수집·저장하고 다시 읽어 원본과 일치하는지 검증한다. 같은 입력을 다시 처리해 중복 행이 생기지 않는지 확인한다.
4. 최초 수집은 최근 30일 콘텐츠부터 시작해 접근 가능한 이전 게시물·릴스까지 진행한다. 계정 조회·도달도 실제로 제공되는 과거 기간 통계를 가져온다. 조회 가능 기간과 실제 처리 범위를 구분한다. 현재 팔로워를 과거 기간 행에 복제하지 않는다. 과거 팔로워 시계열은 원본이 있더라도 현재 시점값 속성에 섞지 않고 추가 매핑 필요로 보고한다.
5. 25개 콘텐츠 단위로 처리 위치, 콘텐츠 ID, 원본 관측 시각, 저장 확인된 키, 실패 항목을 비공개 기록에 남겨 중단 후 이어간다. 원본 내보내기가 제공되면 이용할 수 있지만 지표 정의·날짜 의미를 검증한 뒤 사용한다.
6. 정기 수집 제안은 매일 09:00 Asia/Seoul, 최근 30일 게시물·릴스와 계정 요약이다. 운영 일정과 정기 범위는 아직 사용자 확정 전이다. 초기 구성과 최초 수집은 계속 진행하고, 예약 활성화는 이 항목이 확정된 뒤 수행한다. 첫 저장 검증 후 실제 예약 기능이 제공되면 확정된 일정으로 설정하고 다음 실행 시각을 확인하라. 지원되지 않으면 미설정으로 보고한다. 초기 수집과 정기 수집은 동시에 같은 DB에 쓰지 않는다. 오래된 모든 콘텐츠를 매일 다시 수집하는 것은 제안된 정기 범위에 포함되지 않는다.

## 정확성과 중복 방지

- 팔로워는 수집 시점의 값, 콘텐츠 지표는 원본이 명시한 누적 또는 기간 값, 계정 조회·도달은 원본 집계 기간 값이다. 게시일·관측일·집계 기간을 구분한다. 오늘 읽은 과거 게시물 누적값을 과거 날짜의 일별 실적으로 만들지 않는다.
- 관측일은 실제 수집 시각의 한국 날짜다. 과거 기간을 오늘 조회해도 관측일은 오늘이고 집계 기간만 과거다. 보관한 수집 자료를 저장 재시도할 때는 원래 관측 시각을 유지하고, 원본을 새로 조회했을 때만 새 관측 시각을 부여한다.
- 원본에 없는 숫자는 빈값과 사유로 남긴다. `0`은 실제 0일 때만 쓴다. `1.2만` 같은 축약값은 정확한 정수로 간주하지 않는다. 수집 실패로 기존 정상값을 지우지 않으며, 이전 값을 유지하면 이전 관측 시각을 비고에 남긴다.
- 원본 지표명과 광고 포함 여부를 보존한다. 정의가 다른 조회·재생 등의 값을 합치지 않는다. 콘텐츠 도달을 합쳐 계정 도달로 만들거나, 일별 도달을 합쳐 월간 고유 도달로 만들지 않는다.
- 안정적인 계정·콘텐츠 ID를 우선 사용하고 없으면 정규화한 고유 URL을 사용한다. 제목으로 연결하지 않는다. 키는 아래 요소의 JSON 배열을 직렬화한 텍스트다. null은 문자열이 아닌 JSON null이며, 기간 경계와 시간대 표기를 고정한다.
  - 콘텐츠: `["content", 계정, 콘텐츠]`
  - 콘텐츠 관측: `["media", 계정, 콘텐츠, 관측일, 범위, 집계시작, 집계종료, 원본시간대]`
  - 계정 관측: `["account", 계정, 관측일, 범위, 집계시작, 집계종료, 원본시간대]`
- 같은 키가 없으면 생성, 한 건이면 갱신, 여러 건이면 충돌 보고. 쓰기는 직렬화한다. 생성 요청이 시간 초과되면 먼저 재조회해 실제 저장 여부를 확인한다. 과거 같은 기간을 여러 날 관측한 경우 비교에는 최신 검증 관측 하나만 쓰고 중복 합산하지 않는다.
- 콘텐츠의 최신 지표는 저장·재확인된 동일 시점의 누적 관측 묶음만 반영한다. 적용 가능한 지표가 모두 확인되어야 하며 원본이 명시한 미제공 빈값은 허용한다. 읽기 실패·축약값은 최신 묶음으로 승격하지 않는다. `검증 중`으로 표시한 뒤 묶음 갱신·재확인을 마치고 `검증 완료`로 전환한다.

## 접근과 결과 보고

인증은 서비스의 안전한 로그인·연결 설정으로 처리한다. Business Suite는 인사이트 조회 권한, Notion은 지정 페이지의 하위 페이지·DB 생성·기록 권한이 필요하다. 게시물 발행, 메시지 발송, 광고 결제는 작업 범위가 아니다. 비밀번호·토큰·쿠키, 실제 데이터·대상 페이지 주소를 공개 GitHub에 기록하지 않는다.

마지막에 다음을 보고하라: 실제 대시보드·세 DB URL, 생성·재사용·미완료 항목, 실제 수집 범위와 완료·부분 수집·실패 건수, 첫 저장 및 중복 방지 검증 결과, 재개 위치, 예약 상태와 확인된 다음 실행 시각, 남은 연결·권한 문제. 실제 확인하지 않은 생성·저장·예약을 완료로 표현하지 말라.
