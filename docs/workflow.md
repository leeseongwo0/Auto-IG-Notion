# Instagram → Notion 워크플로

## 1. 실행 전 설정

아래 설정으로 새 공간을 구성합니다. 실제 계정과 상위 페이지는 로컬 설정에서 읽고, DB 주소는 생성 결과로 채웁니다.

| 설정 | 상태 또는 제안 |
| --- | --- |
| Instagram 계정 | Git에서 제외한 `config/local.json`의 `instagram` 항목 |
| 계정 권한 | 프로페셔널 계정 인사이트 열람 가능 — 사용자 확인 |
| 지표 원본 | Meta Business Suite 우선, 필요할 때 Instagram 인사이트로 보완 |
| Notion 데이터베이스 | 지정된 상위 페이지 아래 새 `Instagram 성과` 공간에 콘텐츠·콘텐츠 지표·계정 지표 DB 구성 |
| 실행 도구 | OpenAI Dot; 사용 가능한 연결·브라우저·예약 기능은 실제 환경에서 확인 |
| 관측 기준일 시간대 | Asia/Seoul |
| 실행 주기 | 제안: 매일 09:00 KST; 아직 예약하지 않음 |
| 최초 수집 대상 | 접근 가능한 기존 게시물·릴스와 과거 기간 통계; 기존 Notion 기록 이관 제외 |
| 정기 콘텐츠 대상 | 제안: 최근 30일 내 게시한 게시물과 릴스; 스토리 제외 |
| 계정 지표 집계 범위 | 원본에서 제공하는 기간 확인 후 고정; 최근 30일을 제공하면 우선 사용 |
| 기록 방식 | 콘텐츠 DB는 게시물당 한 행, 콘텐츠·계정 지표 DB는 날짜·집계 범위별 관측 이력 |

30일 콘텐츠 범위는 게시일 기준입니다. 이 기간에 새로 발생한 조회수만 뜻하지 않습니다. 처음 실행할 때 과거 날짜의 관측값을 만들어 넣지 않습니다.

초기에는 [기존 지표 최초 수집](initial-import.md)에 따라 과거 자료를 수집합니다. 과거 기간의 원본 통계를 가져올 때도 관측일은 실제 수집일로 두고, 통계가 설명하는 날짜는 집계 기간에 보존합니다.

## 2. 최초 연결 점검

1. Dot에서 사용할 수 있는 도구와 로그인 상태를 확인합니다. 연결 도구가 필요한 인사이트를 제공하면 활용하고, 화면으로 확인할 경우 표시되는 값을 읽습니다. Dot의 API·예약 지원을 미리 가정하지 않습니다.
2. Business Suite에서 선택된 Instagram 계정이 요청받은 계정과 일치하는지 확인합니다. 계정 요약과 게시물 또는 릴스 한 건의 인사이트가 실제로 열리는지 점검합니다. Instagram 직접 조회로 보완할 때는 지표 정의와 기간이 같은지 확인합니다.
3. [새 구성 명세](notion-layout.md)와 `notion/schema.json`에 따라 대시보드와 세 DB를 만듭니다. 생성·재실행 절차는 `prompts/dot-bootstrap.md`를 따릅니다. 기존 캘린더 구조 확인은 선행 조건이 아닙니다.
4. 쓰기 전에 생성된 DB의 실제 속성을 명세와 대조합니다. 콘텐츠 행과 관측 행을 구분하고 키·관계 대상을 확인합니다. 구성 작업 중 인증이 막혀도 독립적으로 가능한 준비는 진행합니다.
5. 처음에는 계정 요약 한 건과 콘텐츠 한 건을 수집한 뒤 저장할 내용을 검토 가능한 형태로 제시합니다. 수집 권한과 기록 대상이 확인되면 그 범위에서 저장하고, 같은 입력을 다시 처리해 중복이 생기지 않는지 확인합니다.

로그인이나 재인증은 서비스의 로그인 화면 또는 안전한 연결 설정을 통해 처리합니다. 비밀번호·토큰을 문서, 저장소, 실행 보고서에 남기지 않습니다.

## 3. 수집할 데이터

### 공통 정보

| 논리 필드 | Notion 권장 유형 | 규칙 |
| --- | --- | --- |
| 이름 | 제목 | 사람이 알아볼 수 있는 계정·콘텐츠 이름과 기준일 |
| 기록 키 | 텍스트 | 동일 관측을 재처리할 때 사용하는 정확 일치 키 |
| 기록 종류 | 선택 | 계정 / 게시물 / 릴스 |
| 계정 식별자 | 텍스트 | 가능하면 안정적인 계정 ID; 없으면 프로필 URL을 사용하고 변경 추적 |
| 콘텐츠 식별자 | 텍스트 | 콘텐츠 ID 또는 쿼리를 제거한 고유 게시물 URL |
| 원본 링크 | URL | 계정 또는 콘텐츠로 돌아갈 링크 |
| 관측 기준일 | 날짜 | 실제 수집 시각을 Asia/Seoul로 환산한 날짜 |
| 수집 시각 | 날짜 | 시간대가 포함된 실제 확인 시각 |
| 집계 범위 | 텍스트 | 순간값 / 누적 / 최근 30일 등 원본의 의미 |
| 집계 시작·종료 | 날짜 | 기간 지표에만 사용. 원본 시간대와 경계 포함 여부를 비고에 보존 |
| 원본 기간 표기 | 텍스트 | 원본이 보여주는 기간·시간대 그대로; 불명확한 경계를 추측하지 않음 |
| 수집 상태 | 선택 | 완료 / 부분 수집 / 확인 필요 |
| 비고 | 텍스트 | 누락 사유, 원본 지표 이름, 축약값, 원본 단위 |
| 실행 ID | 텍스트 | 이번 실행을 식별하는 값 |

위는 논리 필드 설명이며 실제 속성명·유형은 `notion/schema.json`을 따릅니다. 새 구성에서는 세 DB를 사용합니다. 조회와 도달 등 공통 집계 기간을 쓸 수 없는 지표는 기간별 관측 행으로 나눕니다.

### 계정 요약

- **팔로워 수**: 수집 시점의 순간값. 기간별 순증감으로 해석하지 않습니다.
- **조회·도달**: 원본이 명시하는 집계 기간과 지표 이름을 보존합니다. 예를 들어 최근 30일 도달은 하루 도달이 아닙니다.
- 팔로워 수와 기간 지표를 같은 행에 보관하면 팔로워에는 `수집 시각`, 조회·도달에는 `집계 범위/기간`이 적용됨을 매핑에 명시합니다.
- 매일 관측한 최근 30일 도달을 서로 합산하거나 차감해 일별 도달을 계산하지 않습니다.

### 게시물·릴스

- 콘텐츠 식별자, 종류, 게시 시각, 원본 링크를 수집합니다.
- 조회·도달·좋아요·댓글·저장·공유를 각각 수집합니다. 해당 콘텐츠에서 제공되지 않는 지표는 빈값과 사유를 기록합니다.
- 누적 지표는 해당 관측 시점의 누적값으로 저장합니다. 기간 필터가 있으면 그 기간을 따로 기록합니다.
- 조회, 재생, 도달을 임의로 같은 지표에 합치지 않습니다. 도달은 고유 계정 수이므로 콘텐츠별 도달을 합산해 계정 도달로 표시하지 않습니다.

### 숫자와 누락 처리

- 실제 0만 숫자 `0`으로 기록합니다. 미제공, 접근 불가, 읽기 실패는 빈값과 사유로 구분합니다.
- `1.2만`, `1.2K` 같은 축약값은 원문을 보존합니다. 정확값을 추가로 확인할 수 없으면 정확한 수치 속성에 정수로 넣지 않습니다.
- 음수·잘못된 형식·지표명 불일치를 확인합니다. 플랫폼 정정이나 좋아요 취소로 값이 줄 수 있으므로 단조 증가를 강제하지 않습니다.
- 새 수집이 실패했다고 기존의 정상 수치를 빈값이나 0으로 덮어쓰지 않습니다. 부분 갱신에서는 각 유지 값의 이전 수집 시각을 비고 또는 별도 속성으로 보존합니다.

## 4. 반복 실행

1. 실행 ID와 시작 시각을 기록하고, 같은 대상에 대한 다른 실행이 진행 중인지 확인합니다. 자동 실행과 수동 실행을 포함해 대상 DB의 작성자는 하나로 직렬화합니다.
2. 계정 요약을 읽고 기간을 확인합니다.
3. 콘텐츠 목록을 끝까지 페이지 이동하거나 스크롤해 대상 게시일 범위를 확인합니다. 고정 게시물 때문에 정렬이 바뀔 수 있으므로 오래된 첫 항목에서 탐색을 끝내지 않습니다.
4. 대상 콘텐츠별 인사이트를 읽고 공통 필드와 지표를 정규화합니다. 목록을 끝까지 확인하지 못하면 전체 수집 완료로 보고하지 않습니다.
5. 키로 Notion을 조회합니다. 기존 기록이 없으면 생성하고, 정확히 한 건이면 허용된 지표·메타데이터만 갱신합니다. 두 건 이상이면 중복 충돌로 기록하고 자동 선택·삭제하지 않습니다.
6. 생성 또는 갱신 후 저장된 페이지를 다시 읽어 키, 기간, 지표가 맞는지 확인합니다. Notion에서 확인된 결과만 저장 성공으로 셉니다.
7. 처리 결과와 실패 대상을 보고합니다. 독립적인 콘텐츠 실패가 있으면 나머지를 계속 처리하고 부분 성공으로 종료합니다.

### 중복 방지 키

날짜별 이력의 논리 키입니다. 요소를 순서가 고정된 JSON 배열로 직렬화한 문자열을 실제 키로 사용합니다. 입력에 구분 문자가 들어가도 충돌하지 않으며 수집 시각 자체는 키에 넣지 않습니다.

```text
콘텐츠 기본 행: ["content", "계정 식별자", "콘텐츠 식별자"]
계정 관측: ["account", "계정 식별자", "관측 기준일", "범위", "시작 경계 또는 null", "종료 경계 또는 null", "원본 시간대 또는 unknown"]
콘텐츠 관측: ["media", "계정 식별자", "콘텐츠 식별자", "관측 기준일", "범위", "시작 경계 또는 null", "종료 경계 또는 null", "원본 시간대 또는 unknown"]
```

같은 기준일·같은 집계 범위·동일한 기간 경계의 재실행은 같은 행을 갱신하고, 다음 날의 관측은 새 행을 만듭니다. 최초 매핑에서 원본의 날짜 또는 시각 단위 경계를 어떻게 표기할지 고정합니다. 같은 날이라도 실제 기간 경계가 달라졌다면 별도 관측이며, 시각 단위 기간을 임의로 날짜 단위로 잘라 합치지 않습니다. `누적`에는 기간 경계 대신 고정된 표기를 사용합니다. 기간을 알 수 없는 행은 정상적인 기간 지표와 같은 키를 사용하지 않습니다.

Notion에 고유값 제약이 있다고 가정하지 않습니다. 조회 후 생성만으로 동시 실행 중복을 완전히 막을 수 없으므로 실행 직렬화가 필요합니다. 아직 실행 중인지 확인할 수 없다면 자동 동시 실행을 시작하지 않습니다.

## 5. 실패와 재실행

| 상황 | 처리 |
| --- | --- |
| 로그인 만료·추가 인증 | 해당 서비스 작업을 중단하고 재인증 필요를 보고 |
| 인사이트 권한 없음 | 공개 좋아요 등을 비공개 인사이트 대용으로 쓰지 않고 누락 사유 기록 |
| 일시적 연결 오류 | 최대 3회 재시도, 5초·15초·45초 대기; 서버의 대기 안내가 있으면 우선 적용 |
| 생성 요청 후 시간 초과 | 먼저 키로 재조회. 저장 여부가 불확실하면 생성 요청을 반복하지 않고 확인 필요로 남김 |
| 일부 콘텐츠 수집 실패 | 성공분을 보존하고 실패한 항목만 재시도 |
| Notion 속성 불일치·쓰기 권한 없음 | 쓰기를 멈추고 필요한 매핑 또는 권한을 보고 |

원본 서비스를 다시 조회한 데이터에는 실제 재수집 시각을 사용합니다. 보관한 수집 자료를 저장 재시도하는 경우에는 원래 관측 시각을 유지합니다. 다음 날 다시 조회한 값을 전날 관측값으로 넣지 않습니다.

## 6. 완료 기준

첫 실연동에서 다음을 검증합니다. 현재는 아직 실행하지 않은 항목입니다.

- 계정 요약 1건과 게시물 또는 릴스 1건을 원본에서 읽고 기간·수치를 대조한다.
- 생성한 Notion DB의 속성에 기록한 뒤 다시 읽어 일치 여부를 확인한다.
- 같은 수집 입력을 재처리해 새 중복 행이 생기지 않음을 확인한다.
- 누락 지표를 0으로 쓰지 않으며, 수집 실패가 기존 정상값을 지우지 않음을 확인한다.
- 전체 대상 실행에서 목록 탐색 범위와 성공·부분 수집·실패 건수를 확인한다.

실행 보고서에는 실행 ID, 실제 시작·종료 시각, 대상 계정·기간, 발견·수집·생성·갱신·저장 확인 실패 건수, 누락 항목과 재실행 대상을 남깁니다. 별도 Notion 실행 기록 DB는 기존 구조와 필요를 확인한 뒤 선택합니다.
